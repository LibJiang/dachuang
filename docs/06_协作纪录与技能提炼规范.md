# 协作纪录与技能提炼规范

> **目的**：把每个人每次工作的过程，沉淀成可检索、可复现、可提炼的团队资产；项目推进到一定阶段后，从中提炼出正式的 `skill` 文档。
> **适用范围**：全体成员，**每次完成一次可交付工作后必须写**（代码、文档、实验、调研都算）。
> **一句话规则**：**没有协作纪录的 PR 不合入；没有验证证据的纪录不算完成。**

---

## 一、硬性规则（每次工作后必做）

1. **当天写**：每次工作结束当天内写一篇，不要攒到周末补。
2. **放对位置**：统一放 `docs/records/`，文件名见第二节。
3. **必须可复现**：写清命令、原始输出、波形/报告路径或 PR 链接，禁止只写「已完成」「应该没问题」。
4. **必须写提炼项**：每篇都要有「可提炼经验」一栏，哪怕只有一条。
5. **随代码提交**：纪录和本次改动放在同一分支 / 同一个 PR。
6. **复核检查**：复核人确认纪录合格后，PR 才可合入；不合格则打回补齐。

> 判定「一次工作完成」的标准：有**可交付物**（代码 / 文档 / 实验结论 / 调研结论）+ 有**验证证据**。只开个头、没结果的，不算完成，可以不写；但要在下次纪录里说明。

---

## 二、命名与位置

| 项目 | 规则 |
|---|---|
| 目录 | `docs/records/` |
| 文件名 | `YYYY-MM-DD-成员名-主题.md` |
| 示例 | `2026-11-05-zhangsan-montgomery-modmul.md` |
| 粒度 | 一篇对应一次工作 / 一个主题 |
| 跨天工作 | 在原文件追加章节，不要重复新建 |
| 模板 | 复制 `docs/records/TEMPLATE.md` 后填写 |

- 文件名用英文 / 拼音 + 数字，不用中文，避免跨平台乱码。
- 主题用短横线连接，例如 `ntt-butterfly`、`git-pr-flow`、`kyber-modreduce`。

---

## 三、必填字段（照着模板填）

1. **基本信息**：日期、成员、分支 / PR、关联选题或任务。
2. **本次目标**：一句话说明这次要达成什么。
3. **做了什么**：分点写，对应到文件 / 模块 / 文档。
4. **验证证据**：命令 + 原始结果 + 产物路径（日志、波形、报告、截图、PR）。
5. **问题与解决**：现象 → 定位过程 → 解决办法 → 耗时。
6. **关键决策与理解**：为什么这么做；能否向队友讲清每个 `always` 块在干什么。
7. **未完成 / 待办**：明确标注「未实现」「未验证」，不许含糊。
8. **可提炼经验**：这次有哪些做法、坑、检查项值得沉淀成 skill。
9. **参考**：论文、链接、参考的仓库文件。

> 一页以内即可。重点不是字数，是**证据**和**反思**。

---

## 四、完成标准（DoD 自检）

- [ ] 有明确的可交付物（文件 / 模块 / 文档 / 结论）
- [ ] 有可复现的验证命令与原始结果
- [ ] 问题与解决过程写清，不是只写结果
- [ ] 未完成项已明确标注
- [ ] 至少写了 1 条「可提炼经验」
- [ ] 纪录已和代码一起提交，或在 PR 中链接

任何一条不满足：视为未完成，补齐后再合入。

---

## 五、复核机制

1. **作者自检**：提交前对照第四节逐条打勾。
2. **复核人抽查**：每周随机抽 1 篇，按纪录里的命令复跑一次；跑不通或证据缺失，打回。
3. **每周例会 10 分钟**：过一遍本周纪录，标记「高质量条目」和「需要补课的知识点」。
4. **高质量标准**：别人能照着纪录复现结果，并能看懂你为什么这么做。

---

## 六、从纪录提炼 skill 的流程

> 目标：把零散的个人经验，变成团队可复用的操作手册（最终汇总成 `skill` 文档）。

### 频率
- 每两周小提炼一次；项目结题前做一次总提炼。

### 步骤

1. **收集**：汇总 `docs/records/` 里所有「可提炼经验」条目。
2. **聚类**：把重复出现的做法 / 坑 / 检查项归成主题（如「testbench 自检套路」「Vivado 时序排查」「Git PR 流程」）。
3. **验证**：一个条目至少被 **2 篇纪录 / 2 个人**验证过，才升级为 skill；单人一次的灵感先留在待观察区。
4. **成文**：写入 `skill/<主题>/SKILL.md`，按第七节结构写。
5. **索引**：更新 `skill/README.md`，登记主题、来源纪录、负责人。
6. **回溯**：每个 skill 章节末尾标注来源纪录文件名，方便追溯。

### 目标产物

- 默认：一份团队级 `skill/` 文档（如 `skill/dachuang-collab-sop/SKILL.md`）。
- 如果方向差异大：按方向拆成多份（如 `skill/rtl-verification/`、`skill/vivado-flow/`），但保留统一索引。

---

## 七、skill 文档的标准结构

```markdown
---
name: <主题名>
description: <何时触发；解决什么问题>
---

# <主题名>

## 适用场景
## 前置条件
## 步骤（可执行，带命令）
## 验证标准（怎么算成功）
## 反例与常见坑
## 来源纪录
## 变更记录
```

要求：

- **可操作**：步骤里要有命令、文件路径、判据，不是经验散文。
- **可验证**：每条 skill 都要有「怎么算成功」。
- **可追溯**：标注来自哪些协作纪录。
- **不重复**：和已有文档重复的内容用链接，不复制。

---

## 八、好纪录 vs 不合格纪录

| 不合格 | 合格 |
|---|---|
| 「今天写了 NTT 蝶形，应该没问题」 | 「实现 `ntt_butterfly.v`，用 1000 组随机向量对拍 Python 模型，`iverilog` 输出 `PASS: 1000/1000`，日志见 `docs/records/...`」 |
| 只写结果，不写过程 | 写清「报错现象 → 定位到复位极性写反 → 改 `rst_n` → 复跑通过」 |
| 待办写「继续优化」 | 待办写「关键路径 12.3ns，下一步切两级流水，目标 <8ns，未实现」 |
| 没有问题、没有反思 | 至少记录一个踩过的坑或一个值得复用的做法 |
| 纪录和代码分开提交 | 纪录与代码同分支 / 同 PR |

## 九、示例（节选，完整填写版见 `docs/records/EXAMPLE-record.md`）

```markdown
# 2026-11-05 zhangsan 模乘单元验证

## 基本信息
- 日期：2026-11-05
- 成员：zhangsan
- 分支 / PR：#12
- 关联任务：T1 模约减前置练习

## 本次目标
完成参数化模乘单元 RTL 并用 Python 黄金模型对拍。

## 做了什么
- 新增 `src/arith/modmul.v`
- 新增 `sim/tb_modmul.v`，读取 `data/vectors/modmul.hex`
- 新增 `tools/gen_modmul_vectors.py`

## 验证证据
- 命令：`iverilog -o build/tb_modmul.vvp src/arith/modmul.v sim/tb_modmul.v && vvp build/tb_modmul.vvp`
- 结果：`PASS: modmul 1024 vectors, 0 errors`
- 产物：`docs/records/logs/2026-11-05-modmul.log`

## 问题与解决
- 现象：前 32 组对拍失败，结果为负数。
- 定位：Python 模型用了 `%`，Verilog 用了有符号截断。
- 解决：统一按无符号余数处理，复跑通过。

## 关键决策与理解
- 用组合逻辑实现，当前频率优先；后续若关键路径超标再切流水线。

## 未完成 / 待办
- [ ] 流水线版本（未实现）
- [ ] 与论文 PPA 对比（未验证）

## 可提炼经验
- 随机向量对拍前，先确认 Python 与 RTL 的「负数取模」语义一致。
- testbench 统一打印 `PASS/FAIL + 用例数`，方便回归。

## 参考
- `src/riscv/alu.v`（写法参考）
```

## 十、常见问题

| 问题 | 处理 |
|---|---|
| 太忙没时间写 | 每次收尾留 10 分钟，先填证据，再补反思 |
| 不知道写什么 | 打开 `TEMPLATE.md` 逐项填，写不出说明这次没验证 |
| 纪录太长 | 控制在一页内，重点是证据、坑、决策 |
| 只是看视频 / 读论文 | 也算一次工作，写「学到了什么、能用到哪、还有哪些没懂」 |
| 多人一起做 | 每人各写一篇，或一篇里按成员分节，但要写清各自贡献 |
